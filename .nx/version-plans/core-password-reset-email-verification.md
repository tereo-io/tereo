Password reset and email verification. `POST /v1/password-reset` (public, always `202` before any work is done so nothing about the account leaks through timing or errors; 3 requests per address per hour, which anyone can exhaust for a victim's address) emails a one-time reset link (`PASSWORD_RESET_TTL_SECONDS`, 1 hour) that is redeemed on the existing `/v1/password-setup` routes, which now serve setup and reset links (the `auth.password_setup_tokens` table becomes `auth.user_link_tokens` with a `purpose`); `GET /v1/password-reset/status` tells the sign-in page whether it is enabled. Both link kinds are refused once the user's email domain is SSO-only, and a redeemed reset also clears pending forced-password-change grants. Addresses now carry `email_verified_at` (existing human and guest accounts are marked verified by the migration): `email_verified` in userinfo, ID tokens and `/oauth/introspect` is real instead of always `true`, and users carry `emailVerified` and `emailVerifiedAt`. An address is proven by a verify link (`POST /v1/email-verification`, `EMAIL_VERIFICATION_TTL_SECONDS`, 3 days), a redeemed reset link, first-admin setup, or a provider that vouches for it on an ordinary linked sign-in, invite claim, autoAccept or account link (a forced SSO-required link does not verify); a redeemed setup link does not verify, since its URL is returned to the inviter. An admin changing a user's email unverifies it and sends a verify link (none for an inactive, expired or deactivated user, and the change succeeds without an email connection). `POST /v1/account/email-verification` and `POST /v1/admin/users/:id/email-verification` resend the link (409 `already_verified`, `user_not_verifiable` for service accounts, the system user, deactivated users and expired guests, `email_not_configured`). New events `auth.user.password-reset-requested`, `auth.user.email-verification-sent` and `auth.user.email-verified`; `auth.user.password-set` gains `via`. The admin UI adds Forgot password, Verify email and verification status. Fixed: the admin UI redirected signed-out visitors who opened `/set-password` (guest setup links) to `/`; `/set-password`, `/forgot-password` and `/verify-email` now open signed out.

**Upgrading:** the migration renames `auth.password_setup_tokens` to `auth.user_link_tokens`, so during a rolling deploy pods still on the older image fail on their setup-link routes and in the hourly auth cleanup until replaced. Rolling the image back past this release needs the migration reversed first; the statements are in `packages/tereo/docs/auth.md` (Password links, "Rolling deploys and rollback").
