Client branding for sign-in pages. An admin brands `/login`, `/consent`, `/logout`, `/set-password` and the steps under `/login/*` per client, over an optional default profile and then stock Tereo, field by field: app name, headline, subtitle, sign-in label, notice, logo, dark logo, favicon, background image, `centered` or `split` layout, up to three `https:` footer links, and any of kosmeo's 51 `--k-*` colour variables for light and dark (a strict value grammar; nothing free-form reaches the page). Core injects the result into the app shell for the first paint — a `#tereo-branding` block that is always present on sign-in routes, `null` when unbranded — and `GET /oauth/branding?client_id=` serves the same value for a UI hosted apart. Images are stored once by content in the new `auth-service-branding` bucket (PNG, WebP, JPEG, SVG and ICO by slot, unsafe SVGs rejected, `BRANDING_IMAGE_MAX_SIZE_KB` and `BRANDING_BACKGROUND_MAX_SIZE_MB`), served from `/oauth/branding/assets/:file`, and unreferenced ones expire after 24 hours. New admin API under `/v1/admin/branding` (list, default, per-client profiles, grants, image upload), permissions `branding.read`, `branding.write` and `branding.admin`, and the events `auth.branding.updated`, `auth.branding.deleted`, `auth.branding.grant-added` and `auth.branding.grant-revoked`. A client's owner, or a user granted branding rights on it, may brand that client; the default and `tereo-ui`'s profile are `branding.admin`'s, and `tereo-ui` takes no grants. A provisioning document's `branding` block (default and per-client profiles, image paths inside `PROVISIONING_PATH`) is applied with the set and read-only through the API (`409 managed_by_provisioning` with `provisionedFrom`); removing it keeps the values and makes the profile editable. `applyToConsole` brands the admin console from `tereo-ui`'s profile, else the default, and the Branding page shows stock colours while open. The admin UI gains a Branding page with a live preview.
